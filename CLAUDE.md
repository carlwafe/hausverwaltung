## Projekt

"Mietverwaltung Eutin": Buchhaltungs-/Verwaltungs-App für ein Mietobjekt (~63 Einheiten) mit Mietverträgen, Zahlungen, Kosten, Kautionen, Nebenkostenabrechnung, Jahresübersicht (Einnahmen-Überschuss, Anlage V) und Kontoauszug-Import. Next.js 16 (App Router, Server Actions), React 19, Prisma 7 mit `@prisma/adapter-pg`, Neon Postgres, NextAuth 4 (Credentials, Rollen `ADMIN`/`GAST`), Tailwind 4, Vercel (Blob für Belege/Fotos). UI-Texte, Kommentare und Domänenbegriffe sind Deutsch — beim Schreiben von Code/Kommentaren daran anpassen. Konversation mit dem Nutzer auf Deutsch.

```bash

npm run lint         # eslint
npx tsc --noEmit     # Typecheck (kein separates Skript); prüft auch scripts-tmp/ — Fehler dort (alte Einmalskripte mit veralteten Signaturen) ignorieren, nur Fehler in src/ zählen
npm run build        # wake-db → migrate-with-retry → next build (braucht erreichbare DB); lokal scheitert der Typcheck-Schritt an denselben scripts-tmp-Altlasten — als Prüfung genügt „Compiled successfully“ (Vercel hat scripts-tmp nicht)
npx prisma migrate deploy && npx prisma generate   # Migrationen lokal anwenden, Client neu erzeugen
npx tsx scripts-tmp/xyz.ts                          # Einmal-Skripte gegen die DB (siehe unten)
```

Es gibt keine Testsuite. Verifiziert wird über `tsc`, `eslint`, `next build` und eigene `tsx`-Skripte gegen die DB; die reine Rechenlogik (`src/lib/*`) lässt sich gut direkt mit `tsx` aufrufen.

- Nach jeder Schema-Änderung `prisma generate` ausführen **und den Dev-Server neu starten** (bei Fehlern wie "Unknown field … for include" oder komischem Verhalten: laufenden `next dev` beenden, `.next` löschen, neu starten — der Server hält sonst den alten Prisma-Client). Ebenso nach einem Branch-Wechsel: ein vorher gestarteter `next dev` zeigt neue Seiten/Komponenten sonst nicht. Next erlaubt nur **einen** `next dev` je Ordner (Lock in `.next/dev`): Hält ein anderer Chat den Server auf :3000, scheitert `preview_start` auch mit der :3001-Konfiguration ("Another next dev server is already running") — dann den Nutzer fragen, ob der Server (PID aus der Meldung) neu gestartet werden darf, statt ihn eigenmächtig zu beenden. Ein frisch gestarteter Server kompiliert Login und Seiten beim ersten Aufruf langsam (Anmelden im Browser-Pane dann 10 s warten, ggf. zweimal).
- `tsx` lädt keine `.env`-Dateien selbst: vorher `set -a; . ./.env; set +a` (lokale DB `mietverwaltung_eutin`) bzw. `. ./.env.prod-admin.local` (Produktion, Neon) sourcen.

- Die `.env*`-Dateien (`.env`, `.env.local`, `.env.prod-admin.local`) sind git-ignoriert und liegen im Hauptordner `/Users/felixwaller/Claude Projects/Neuer Ordner/`; nur `.env.example` (Variablenvorlage) ist eingecheckt. `.worktreeinclude` kopiert die drei Dateien in neue Worktrees (`.claude/worktrees/…`) — auch die Produktions-Zugangsdaten. Fehlen sie in einer älteren Sitzung/einem älteren Worktree, von dort kopieren oder direkt per absolutem Pfad sourcen, z.B. `set -a; . "/Users/felixwaller/Claude Projects/Neuer Ordner/.env.prod-admin.local"; set +a`. Der Ordner `/Users/felixwaller/qwer/Neuer Ordner` ist kein Repo (nur `src` und `.claude`) — im Hauptordner arbeiten.
- Temporäre Skripte gehören nach `scripts-tmp/` (in `.gitignore`). Gezielt stagen: `git add -A src prisma` plus bei Bedarf `CLAUDE.md`, `docs/`, `package.json`/`package-lock.json`, `scripts/`, `.gitignore` (die `-A src prisma`-Form lässt diese sonst aus) — nie `git add -A`; vor dem Commit `git status` prüfen. Stolperfalle bei parallelen Chats im Hauptordner: `git add -A src prisma` nimmt auch deren **nicht committete** Dateien mit (neue Dateien erscheinen erst während der Arbeit), und `prisma/schema.prisma` kann Änderungen eines anderen Chats enthalten, die man nicht mitcommitten darf. **Neue Dateien zuerst committen:** Importiert eine bestehende Datei eine neue (z.B. eine ausgelagerte Hilfsfunktion), kann ein anderer Chat mit `git add -A src prisma` die geänderte Datei samt Import mitcommitten und pushen, bevor die neue Datei im Repo liegt — der Vercel-Build scheitert dann (am 23.10.2026 passiert). Deshalb die neue Datei zuerst committen und pushen oder beides gemeinsam. Deshalb nach dem Stagen immer `git diff --cached --name-only` prüfen, fremde Dateien mit `git restore --staged <datei>` wieder herausnehmen (die Arbeitskopie bleibt unberührt) und bei gemischten Hunks nur den eigenen Teil stagen: HEAD-Stand der Datei + eigene Änderung in eine Temp-Datei schreiben, `git hash-object -w <datei>` und `git update-index --cacheinfo 100644,<blob>,<pfad>` (kein `stash`/`checkout --`). **Schema und Migration immer im selben Commit:** Ein anderer Chat, der `git add -A src prisma` ausführt, nimmt `prisma/schema.prisma` mit allen Spalten mit, die du schon eingetragen hast — ohne deine noch ungestagte Migration; wird das gepusht, fragt die Produktion Spalten ab, die es dort nicht gibt (P2022). Deshalb die Migration zuerst committen und pushen oder beides gemeinsam, und in der Schema-Datei **nicht `prisma format` laufen lassen** (richtet die ganze Datei neu aus und erzeugt einen riesigen Diff, der mit den Änderungen anderer Chats kollidiert). **Heredocs mit Backticks:** Ein nicht in Anführungszeichen gesetzter Heredoc (`<<EOF`) führt `` `…` `` im Text als Befehl aus und verschluckt das Wort (so verlor ein Schema-Kommentar „bezeichnung“) — bei Texten mit Code-Backticks immer `<<'EOF'` verwenden und danach prüfen. **Gleiche Skriptnamen in `scripts-tmp/`** (z.B. `testnutzer.ts`) überschreiben sich zwischen parallelen Chats — beim Prüfen eigene Namen mit Präfix verwenden und vor dem Aufruf kurz lesen, was die Datei tut (ein fremdes Skript mit anderer Argumentreihenfolge hat einmal eine Datei mit Zugangsdaten in den Projektordner geschrieben).

## Deployment

Push auf `main` → Vercel baut und veröffentlicht automatisch (Repo `carlwafe/hausverwaltung`). Der Build führt `prisma migrate deploy` aus (`scripts/migrate-with-retry.mjs`, bevorzugt über Neons direkten Endpunkt ohne `-pooler`, weil die Advisory-Lock über den Pooler nach abgebrochenen Builds hängen bleibt → P1002). Deploy-Status: `npx vercel ls`, Log: `npx vercel inspect <url> --logs`. Migrationen sind handgeschriebenes SQL unter `prisma/migrations/<zeitstempel>_name/`; Schema in `prisma/schema.prisma` parallel pflegen. Die Produktions-DB ist von der Entwicklermaschine aus gelegentlich nicht erreichbar (ETIMEDOUT) — dann erneut versuchen, nicht raten. Fehler aus Server Actions zeigt der Browser in Produktion nur als "Minified React error #441" (Meldung ausgeblendet); die echte Meldung steht in den Runtime-Logs: `npx vercel logs --environment production --since 1h -q <pfad> -x` (die SSL-"SECURITY WARNING"-Zeilen dort sind harmlos). **Spalten entfernen braucht zwei Deploys:** `prisma migrate deploy` läuft im Build, bevor die neue Version live ist — die alte Version fragt die gelöschte Spalte noch ab und wirft P2022 („column … does not exist“, am 08.10.2026 ≈ 1 Minute lang auf Dienstleister, Tickets und Startseite). Erst den Code deployen, der die Spalte nicht mehr nutzt, dann die Migration mit `DROP COLUMN` in einem eigenen Push; neue (nullable) Spalten sind dagegen unkritisch. Hängt trotzdem eine Advisory-Lock (P1002 in jedem der 5 Versuche): Ursache ist eine im Pooler zurückbleibende `idle`-Verbindung eines vorherigen abgebrochenen Builds (`select l.pid, a.state from pg_locks l join pg_stat_activity a on a.pid = l.pid where l.locktype = 'advisory'`) — sie nur mit ausdrücklicher Freigabe des Nutzers per `pg_terminate_backend(pid)` beenden (siehe „Arbeitsweise“); danach den fehlgeschlagenen Deploy erneut anstoßen (`npx vercel redeploy <url>`).

**Vercel-Kontingent (Free-Tarif, 4 h „Fluid Active CPU“ pro Monat, Stichtag der 8.):** Verbrauch, Gegenmaßnahmen und Regeln (z.B. `prefetch={false}` an Tabellen-Links, keine schweren Neuberechnungen per `revalidatePath`, Berichte erst auf Knopfdruck) stehen in `docs/deployment-vercel.md` — vor neuen Tabellen-Links, Inline-Aktionen auf schweren Seiten oder neuen schweren Seiten lesen.

## Architektur

**Begriffe.** `Haus` = physisches Bauwerk (in der UI „Gebäude“; fasst ggf. mehrere Hausnummern zusammen, optional), `Gebaeude` = Hausnummer/Adresse, `Einheit` hängt an `Gebaeude` (Hierarchie `Haus` → `Gebaeude` → `Einheit`). Bei „Gebäude/Haus“ in dieser Datei im Zweifel das Modell meinen.

**Journal-Modell (Kern).** Fast alles Finanzielle ist eine Zeile in der einen Tabelle `Buchung`, typisiert durch den Katalog `Buchungsart` (Flags `kontokreis`, `zahlungswirksam`, `eurRelevant`). Beispiele: `MIETZAHLUNG`, `KOSTENPOSITION`, `KAUTION_*`, `NEBENKOSTENAUSGLEICH`, `MAHNGEBUEHR` (= Sonderforderung auf dem Mieterkonto, ohne Geldfluss, nicht EÜR; positiv = Forderung, Vorzeichen allgemein = Wirkung aufs Mietkonto), `SONDERZAHLUNG` (Zahlung darauf), `KAUTION_EINBEHALT` (negativ, kein Bankfluss, EÜR-relevant). Die Seiten `zahlungen`, `kosten`, `kautionen`, `kontostand` usw. sind Sichten auf dieselbe Tabelle (`src/lib/buchungsjournal.ts`, `kontostand.ts`, `mieterkonto.ts`).

**Storno statt Ändern.** Buchungen sind unveränderlich (DB-Trigger `buchungen_unveraenderbar`, Migration `20260920190000`): kein UPDATE/DELETE, nur Verweisfelder dürfen von NULL auf einen Wert wechseln (`storniertDurchBuchungId`, `bezugTyp/bezugId`). "Bearbeiten" = `storniereBuchung` (`src/lib/buchung-storno.ts`) + Neuanlage; "Löschen" = stornieren. Jede Abfrage/Summe muss `...AKTIVE_BUCHUNG_FILTER` verwenden. Zuordnungsfelder (Gebäude/Haus/Kostengruppe/Einheit/Mietvertrag) lassen sich nachträglich nicht umhängen — ebenfalls Storno + Neuanlage. Aufteilen von Zahlungen/Kosten erzeugt Teile mit gemeinsamer `aufteilungGruppeId`; Rückgängig-Logik in `src/lib/aufteilung-aufheben.ts`. Aufgeteilte Buchungen sind in den Tabellen mit ✂ gekennzeichnet (Zahlungen, Kautionen); Aufteilen/Rückgängig läuft über die Detailseite der Buchung. Stolperfalle bei einer gemischten Aufteilung (Zahlung in Miete + Kostenposition, z.B. eine Rücklastschriftgebühr): Rückgängig muss den Kosten-Teil mit umgekehrtem Vorzeichen zurückrechnen (siehe „Vorzeichenkonventionen") und eine daran verknüpfte Gebühren-Forderung mitstornieren — sonst bleibt sie als Karteileiche auf dem Mieterkonto stehen bzw. der wiederhergestellte Betrag stimmt nicht.

**Wer hat gebucht.** Es gibt keinen expliziten Stornogrund in der DB (bewusst — üblich ist nur Original+Gegenbuchung, kein Freitext); `Buchung.erstelltVon` (Benutzerkennung, `benutzerLabel()` in `src/lib/session.ts`) wird dagegen bei jeder Neuanlage **und** jedem Storno gesetzt — auf den ausführenden Nutzer, nicht auf den des Originals, da der Storno eine eigene Handlung ist. Neue Aufrufstellen, die `Buchung` erzeugen oder `storniereBuchung` aufrufen, müssen `erstelltVon` mitgeben (dritter, nicht-optionaler Parameter). Angezeigt wird `erstelltAm`/`erstelltVon` auf den Detailseiten (`/zahlungen/[id]`, `/kosten/[id]`, `/nebenkostenausgleich/[id]`) über `BuchungsartInfo` (optionale Props `erstelltAm`/`erstelltVon`, `src/components/buchungsart-info.tsx`), auf `/kautionen/buchung/[id]` in einer eigenen Zeile „Erstellt“ (dort ohne `BuchungsartInfo`) — ohne Kennung (Altbestand) nur das Datum, kein Platzhaltertext.

**Kommentar zur Buchung.** Auf der Detailseite einer Zahlung (`/zahlungen/[id]`, alle drei Ansichten: Mietzahlung, Gebühren-Zahlung, Gebühren-Forderung/NK-Verrechnung) lässt sich ein interner Freitext-Kommentar (max. 1.000 Zeichen) erfassen, ändern und durch Leeren entfernen; Gäste sehen ihn nur. Da Buchungen unveränderlich sind, liegt er in der eigenen Tabelle `buchung_kommentare` (`BuchungKommentar`, höchstens einer je Buchung, mit `geaendertVon`/`aktualisiertAm`), Aktion `speichereBuchungKommentar` (`buchungen/actions.ts`), Komponente `src/components/buchung-kommentar.tsx` (hält ihren Zustand selbst, kein `revalidatePath`). Stolperfalle: „Bearbeiten“, „Umbuchen“, „Aufteilen“ und „Aufteilung rückgängig“ sind Storno + Neuanlage — der Kommentar würde an der stornierten Zeile hängen bleiben. Deshalb kopiert `uebernehmeBuchungKommentar` (`src/lib/buchung-kommentar.ts`) ihn auf die neue(n) Buchung(en) (beim Aufteilen nur auf die Zahlungsteile, nicht auf Kosten-/Kautionsteile); am stornierten Original bleibt er als Historie. Wer einen neuen Weg einbaut, der eine Zahlung per Storno ersetzt, muss ihn ebenfalls aufrufen. Angezeigt wird der Kommentar bisher nur auf der Zahlungs-Detailseite (nicht in Listen, Kosten- oder Kautionsseiten).

**Vorzeichenkonventionen (Stolperfallen).** Zahlungen/Kaution/Ausgleich tragen das Bankvorzeichen (ausgehend negativ). Eine `KOSTENPOSITION` ist dagegen positiv = Ausgabe, negativ = Gutschrift (also umgekehrt zum Bankbetrag; beim Aufteilen einer Zahlung in Kosten wird das Vorzeichen gedreht). `NEBENKOSTENAUSGLEICH`: negativ = Auszahlung an den Mieter. Verrechnungen mit Nebenkostenabrechnung laufen über `src/lib/nk-verrechnung.ts` (`NK_AUSGLEICH_ODER_VERRECHNUNG`, `nkBegleichung`): Zuordnung zur Abrechnung über Mietvertrag + Jahr (nicht Positions-ID, die sich bei "Neu berechnen" ändert). Der gespeicherte `saldo` einer Abrechnungsposition ist Vorauszahlung − Kosten (positiv = Guthaben); der Reiter "Nebenkostenabrechnung" auf der Mietvertragsseite zeigt ihn nach Muster umgekehrt als Kosten − Vorauszahlung (Nachzahlung +, Guthaben −) — z.B. gespeichert +120 € = dort −120 € Guthaben.

**Schreibende Aktionen.** Server Actions (`"use server"`-Dateien `actions.ts` neben den Seiten) beginnen mit `requireEditor()` (`src/lib/session.ts`; `GAST` = nur lesen), rufen nach dem Schreiben `revalidatePath` für alle betroffenen Seiten auf. Formulare: entweder `useActionState` + `runFormAction` oder Aktionen, die `string | null` zurückgeben. Meldungen für den Nutzer (Validierung, fachliche Prüfungen, Gastzugriff) nie mit `throw new Error` — in Produktion überträgt Next von geworfenen Fehlern nur den Digest, im Browser steht dann nur eine generische Meldung. Stattdessen `throw new AktionsFehler("…")` bzw. `throw zodFehler(parsed.error)` (`src/lib/aktion.ts`) und die Aktion mit `export const x = mitMeldung(async function x(…) { … })` umschließen: der Wrapper gibt die Meldung als Rückgabewert zurück; unerwartete Fehler (Prisma usw.) bleiben normale Errors und erscheinen generisch (Details in den Vercel-Logs). Nur Aktionen umschließen, deren Rückgabewert ausgewertet wird (`runFormAction`, `useActionState`) — bei `<form action>`/Buttons ohne Auswertung würde die Meldung sonst verschluckt. Wiederverwendbare UI: `DataTable` (Sortierung/Suche/Filter/Auswahl), `DateInput` (Datum mit Auto-Sprung), `SubmitButton`, `DeleteButton` (ist selbst ein `<form>` — nicht in andere Formulare schachteln), `MietvertragAuswahl` (Suchauswahl für beliebige `{id,label}`-Listen). Stolperfallen der Suchauswahl: Das Panel darf bei Scroll/Resize nicht schließen, sondern muss sich neu positionieren (auf dem Handy löst schon die Tastatur beides aus; sie verdeckt sonst die Liste) — und eine vorgefilterte Liste gehört in `defaultKandidaten`, `kandidaten` muss die volle Liste bleiben, sonst findet die Namenssuche nichts außerhalb der Vorauswahl (Beispiel: Mietvertrag im Ticket-Formular nach gewählter Einheit). Stolperfalle: viele Einzel-Updates in einer `prisma.$transaction` überschreiten über Neon das 5-s-Limit (P2028, alles wird zurückgerollt) — Sammeländerungen nach Zielwert gruppieren und per `updateMany` schreiben (Beispiel: `speichereAnreden` in `mieter/actions.ts`). Auth-Schutz für alle Routen über `src/proxy.ts` (NextAuth-Middleware). Tab-Titel ("Seite · Mietverwaltung Eutin") setzt `NavBar` clientseitig per `document.title` aus der Liste `SEITENTITEL` in `src/components/nav-bar.tsx` (längster passender Pfad, kein Next-`metadata`) — neue Seiten dort eintragen, sonst zeigt der Tab nur "Mietverwaltung Eutin". Stolperfalle: Next setzt den Titel aus den Layout-Metadaten bei jeder Navigation neu, auch bei bloßem Wechsel der Suchparameter (z.B. Ordner in `/dokumente`) — ein einmaliges `document.title = …` im Effekt genügt nicht; `NavBar` beobachtet deshalb `document.head` per `MutationObserver` und zieht den Titel nach (am 09.10.2026 behoben, vorher zeigte `/dokumente` nur den Standardtitel).

**Sortierung.** Einheiten/Gebäude/Häuser werden nicht alphabetisch, sondern in der Haus-Reihenfolge des Objekts sortiert (`einheit-sort.ts`, `sort-einheiten.ts`, `gebaeude-gruppen.ts`). Stolperfalle in Tabellen: Gibt das `sortValue` einer `DataTable`-Spalte den Bezeichnungstext zurück, sortiert die Spalte alphabetisch ("HS 15" vor "HS 9") — für Einheiten-Spalten stattdessen im Server den Rang mit `sortEinheitenNachGebaeude` berechnen (Abfrage braucht `einheit.gebaeude.haus.gebaeude`) und als Zahl mitgeben (Beispiel: `einheitRang` in Offene Posten). Ohne aktive Spaltensortierung behält die `DataTable` die Reihenfolge der übergebenen Zeilen, die Standardsortierung wird also in der Seite festgelegt. Dasselbe gilt für Auswahllisten (Dropdowns): Einheiten über `sortEinheitenNachGebaeude`, Adressen/Gebäude über `sortGebaeudeNachHaus` (`src/lib/sort-gebaeude.ts`, Haus-Reihenfolge, dann Hausnummer numerisch, ohne Haus ans Ende), Häuser über `vergleicheHaus` — nicht per `localeCompare` auf dem Label ("Haus 10" käme sonst vor "Haus 2"). Die Kosten-Auswahl (`gruppiereGebaeude`, Gruppen „Einzelne Adresse“/„Einzelne Wohnung“) sortiert so; die Abfrage muss das Haus samt seiner `gebaeude` mitladen (`haus: { include: { gebaeude: true } }`), sonst fehlt der Fallback für Häuser ohne gesetzte Reihenfolge. Bewusst alphabetisch bleiben Namenslisten (Kostenarten, Mieter nach Nachname, Dienstleister).

## Arbeitsweise in diesem Repo

- Änderungen werden nach Verifikation (`tsc`, `eslint`) direkt committet und nach `main` gepusht (löst den Produktions-Deploy samt `prisma migrate deploy` aus); Commit-Nachrichten deutsch. Migrationen, die bestehende Daten ändern oder löschen, vor dem Push zeigen und freigeben lassen.
- Wird eine fachliche/buchhalterische Entscheidung getroffen (z.B. wie ein Sonderfall gebucht wird, welche von mehreren Erfassungswegen der bevorzugte ist), am Ende der Aufgabe nachfragen, ob sie dokumentiert werden soll: **in der App** (Hinweistext an der passenden Stelle, z.B. beim Formular oder auf der Listenseite) **und in der passenden Datei unter `docs/`** (siehe „Fachdokumentation“; kurz, ohne Mieternamen oder andere personenbezogene Daten — Beispiele anonym mit Beträgen; `CLAUDE.md` selbst bleibt schlank: nur Befehle, Kernarchitektur und Arbeitsregeln, Fachliches nach `docs/`, `docs/` bei neuen Dateien in der Tabelle oben ergänzen).
- Im Hauptordner arbeiten oft mehrere Chats gleichzeitig: vor Branch-Wechsel, Löschen oder Push `git fetch` + `git status` prüfen, fremde nicht committete Änderungen nicht anfassen (kein `stash`/`checkout --`/`reset`), Branches nur löschen, wenn `git log origin/main..<branch>` leer ist. Auf einen anderen Branch nur wechseln, wenn er auf denselben Commit wie `HEAD` zeigt (dann bleiben Arbeitsbaum und Staging unverändert).
- Änderungen an Produktionsdaten (Buchungen, Verträge, Skripte gegen die Produktions-DB, `pg_terminate_backend`) erst nach ausdrücklicher Freigabe des Nutzers für die konkrete Änderung; vorher immer den Ist-Zustand lesend prüfen. Produktions-Skripte sonst nur lesend.
- Änderungen an Rechenregeln der NK-Engine: vorher mit einem Leseskript in `scripts-tmp/` (Engine-Kopie mit neuer Regel vs. `src`, gleiche Daten aus `ladeBerechnungsdaten`) zeigen, welche Positionen sich wie ändern. Gespeicherte Abrechnungen ändern sich erst durch "Neu berechnen" — bei bereits verschickten Abrechnungen braucht der betroffene Mieter eine korrigierte Fassung.
- Änderungen an den Erkennungsregeln des Kontoauszug-Imports (`src/lib/import/*`: Muster in `bank-csv.ts`, Klassifizierung, Kostenart-/Mietvertrag-Vorschläge): vorher/nachher mit einem Leseskript in `scripts-tmp/` gegen die bestehenden Buchungen prüfen. Alle aktiven Buchungen mit `rohdaten` (`AKTIVE_BUCHUNG_FILTER`; Storno-Gegenbuchungen tragen dieselben Rohdaten und sonst doppelt zählen) durch die neue Regel schicken (Verwendungszweck und Bankbetrag aus den Rohdaten, nicht `Buchung.betrag`: aufgeteilte/umgedrehte Buchungen weichen ab) und die Treffer mit der tatsächlich gebuchten Art/Kostenart vergleichen — jeder Treffer, der anders gebucht ist, ist ein Widerspruch zur bisherigen Praxis (Regel anpassen oder Entscheidung klären), jede schon so gebuchte Zeile, die nicht erkannt wird, eine Lücke. Vorher auch in dieser Datei und in den Hinweistexten der App nachsehen, ob die Praxis schon festgehalten ist. Beispiel: Eine als „Sonderzahlung" geplante Gebühren-Erkennung widersprach so der bisherigen Buchung als Kostenposition „Mahngebühren".
- Altdaten vor dem Buchhaltungsbeginn (Kautionen, Mietbeginn/-ende) stammen aus den E-A-Aufstellungen des Vorverwalters (iCloud-Ordner "Eutin/E:A Austellung"): Konto 3500 = Kautionsverbindlichkeiten (Einzahlung/Anlage/Auflösung/Einbehalt), Mieterzeilen = Jahresmiete je Mieter (→ Monate → Ein-/Auszug); die Kautionskonto-Nummer 06**JJ**… verrät das Eröffnungsjahr. Ohne Beleg keinen Kaution-Datensatz mit geratenem Betrag anlegen. Die Kontonummern dort nicht als Sachkonten übernehmen (siehe „Kontenrahmen“).
- Berichte des Vorverwalters (PowerHaus-PDFs) in CSV umwandeln, App-Quartals-/Jahresübersicht und Kosten damit abgleichen: `docs/abgleich-vorverwalter.md`.
